1 Scope, Traceability, and Notation
1.1 Purpose
This book documents the mathematical and statistical behavior that MethylPipeline actually
implements. It is not a historical reconstruction of the first design notes, and it is not a promise
about future refactors. The source of truth is the current code under packages/.
That rule has two consequences:
1. If the code and an older markdown document disagree, the code is canonical.
2. If the code uses an approximation or heuristic, the book says so explicitly instead of rewriting
it into a cleaner but false theory story.

1.2 What Counts As “Theory” In This Repository
The repository mixes several kinds of methodology. For publication-quality documentation it is
important to separate them.

1.6 Cross-Cutting Assumptions
Several assumptions recur across the repository:
• Loci are treated as conditionally independent inside the classifier score, even though methylation
along the genome is correlated.
• Multiple-testing corrections are applied across many dependent loci and, downstream, across
aggregated genes. This is standard practice but should not be oversold as exact finite-sample
control.
• Some packages operate on summaries rather than raw per-read data. That preserves scalability,
but it changes the interpretation of rank tests and distribution overlap.
• Downstream packages use external services and curated priors. Those are part of the workflow,
but they are not internal statistical estimators.

This book is organized into four parts.
Part I: Mathematical and Statistical Foundations covers the algorithms and estimators
in order from the lowest shared layer to the downstream applications. Readers interested in the
production classifier should start with Chapter 2, then continue through Chapter 3, Chapter 4,
and Chapter 5. Readers interested in biological interpretation should continue to Chapter 7 and

3 MethylCentroid
3.1 Role
methylcentroid is the package that turns a cohort of samples into a reusable centroid object. The
heavy mathematical lifting is delegated to methylutils, but methylcentroid fixes the operational
semantics of what a centroid means in this repository:
• which samples are aggregated,
• how coverage outliers are handled,
• which sufficient statistics are persisted, and
• how the resulting HDF5 artifacts are organized for downstream steps.
The main implementation lives in packages/methylcentroid/methyl_centroid/methyl_centroid.py,
with accumulation handled by methyl_utils/core/centroid_builder.py.

3.5 Auto-Cap Heuristic
The package documentation describes automatic coverage capping through IQR-style heuristics
computed from sampled positions. That should be interpreted as an engineering rule:
𝑛cap ≈ 𝑄3 + 𝑘 ⋅ IQR,
with implementation-specific sampling and fallbacks. This is useful operationally, but it is not a
statistically identified parameter.

3.6 Why Histograms Matter
The centroid builder stores histogram counts even though the mean and variance are already
available. That is because the downstream detector and classifier do not rely only on moments.
They reconstruct empirical distributions from the binned counts and then use those reconstructed
distributions for overlap calculations, KS testing, and classification.
This makes methylcentroid a crucial bridge package: it is the step where sample-level methylation
is transformed into an empirical-distribution object that later packages can reuse without reloading
the full cohort.

3.7 Publication Guidance
For publication text, the safest description is:
• methylcentroid constructs empirical per-locus cohort summaries,
• it preserves both moments and histogram information,
• it optionally reduces extreme coverage through binomial thinning, and
• it is upstream of all ECDF-based detector and classifier logic.
The package should not be described as fitting a parametric methylation model. It is a summary
constructor for the nonparametric empirical-distribution path.

4 MethylDetector
4.1 Role
methyldetector turns aligned centroids into a filtered set of differential methylation positions
(DMPs) and exports the classifier artifacts used downstream. The main implementation is
packages/methyldetector/methyl_detector/core/methyldetector.py.
Conceptually, the detector is a two-stage pipeline:
1. statistical screening of loci, and
2. biological prioritization and export.
That split is important. The code does not rely on a single monolithic significance score.

4.2 Alignment And Candidate Set
The detector starts from aligned centroid pairs, typically one control centroid and one disease
centroid for a given chromosome and context. The alignment step reduces both centroids to the
common set of genomic positions and propagates the empirical summaries described in Chapter 2
and Chapter 3.
Let ℐ denote the set of aligned loci under consideration for one comparison.

4.3 Statistical Screening
The detector supports two closely related statistical paths:
• a histogram-based path through MethylCentroidPair.compare_centroids(), and
• a more precise ECDF path that recomputes KS statistics directly from reconstructed empirical
distributions.
In both cases the active workflow is:
1. compute one p-value 𝑝𝑖 per locus 𝑖 ∈ ℐ,
2. adjust all p-values to q-values using Storey q-values,
3. keep loci satisfying the configured q-value threshold and any minimum effect thresholds.

4.4 Biological Ranking
Once a statistically filtered set exists, the detector ranks loci using the canonical effect score
introduced in Eq. 2.10. This gives a second set of priorities that is explicitly biological or practical
rather than inferential.
The central design choice is that a locus can be:
• statistically strong but biologically modest,
• biologically large but not significant after multiplicity correction, or
• both.
The detector keeps these notions separate instead of compressing them into one scalar.

4.6 Context And Chromosome Granularity
The detector is designed to run at chromosome and context granularity. In practical terms this
means:
• each classifier artifact is tied to a specific chromosome,
• contexts such as CG, CHG, and CHH can be modeled separately or together, and
• any final multiclass or multi-chromosome system is assembled later by methylclassifier.
That architecture keeps detection local and composable, but it also means that downstream fusion
is not part of the detector’s statistical test itself.

The detector does more than report DMPs. It also packages the information needed by the ECDF
classifier:
• the filtered DMP positions,
• per-class centroid histograms over those positions,
• directions of methylation change, and
• feature weights such as effect size.
Mathematically, this means the detector defines the feature space and the feature weighting scheme
for the classifier. The classifier is therefore downstream of detector choices even when its own scoring
rule is fixed.

4.8 Discovery versus prediction exports
Interpretation workflows (mapping DMPs to genes, pathway enrichment, comparing stages) benefit
from broader, biologically coherent DMP lists. Predictive modeling benefits from smaller,
stable feature sets chosen without conflating biological narrative with classification utility.
The implementation therefore supports two coordinated outputs when dmp_export_mode=dual
(default in project configs):

• dmps-{chrom}-discovery.csv: all biologically filtered loci after importance ranking, without
the effect-size elbow used to trim the classifier panel (unless discovery_dynamic_dmp_cutoff_enabled
is turned on).
• dmps-{chrom}-classifier.csv: the prediction panel after the same elbow heuristic as before, or after optional validation balanced-accuracy optimization (classifier_dmp_selection=featurecuts_
when validation samples are configured.
The saved ECDF classifier pickle always uses the classifier panel, not the discovery table.
MethylMapper and MethylEnricher should read the discovery glob (for example dmps-*discovery.csv). Multiclass merge utilities resolve dmps-*-classifier.csv automatically when
present.
For strict evaluation of a deployed classifier, feature selection must be performed inside each outer
training fold (for example by running detection on fold-specific centroids, as in Monte Carlo train
splits); discovery lists built on all samples may still be reported for mechanism, but they must not
be the sole basis for performance claims unless that design is stated explicitly.

4.9 Production Freeze Panel
In the production workflow (Chapter 12), the detector can bypass statistical and biological discovery
entirely and instead operate from a fixed list of pre-selected loci. This is configured via the
fixed_dmp_panel parameter in step_config.detection.

25

When fixed_dmp_panel is set to a path pointing at a CSV file that contains at minimum the columns
chromosome and position, the _run_multi_context method short-circuits the entire discovery
pipeline. No centroids are compared, no KS statistics are computed, and no biological filtering is
applied. The columns context, effect_size, statistical_dmp, and biological_dmp are inferred
or set to unit defaults for any that are missing from the file. The result object is constructed
directly from the loaded rows, with biological_retention_rate = 1.0 and n_statistical_dmps
= n_biological_dmps = n_classifier_dmps all equal to the CSV row count.
This mechanism serves the production workflow where:
1. DMP positions were already validated across many Monte Carlo splits (stability analysis),
2. only the most reliably recurring positions are retained in the stable panel, and
3. the final model must use exactly those positions on the full dataset without re-running
discovery.

4.10 DMP Coverage in New Samples
A frequently encountered diagnostic problem is low DMP coverage in validation or prediction
samples: the classifier reports that only 10–30% of DMP positions have usable observations in a
given sample. The root cause is almost always a mismatch between two coverage thresholds:
• min_coverage in step_config.centroid.base_config — the minimum coverage required
for a locus to be considered by centroid construction and DMP detection during training.
• min_sample_coverage in step_config.detection — the minimum coverage required for a
locus to be usable in a new sample during classification.

26

If centroid construction required min_coverage = 4 but min_sample_coverage is left at its default
of 10, any locus with between 4 and 9 reads in a test sample will be dropped. Since typical WGBS
data is sequenced at moderate depth and coverage varies across the genome, a large fraction of the
60 000 – 200 000 DMP positions selected during training may fall in this 4–9 read range in test
samples, causing the effective feature matrix to collapse to 20% of its intended size.
The observable symptom is:
sample_dmp_coverage.dmps_used_fraction_median < 0.5
in validation_metrics.json. Values below 0.3 indicate severe coverage mismatch and nearly
always lead to prediction dominated by the majority class.
Recommended practice: Set min_sample_coverage equal to the centroid min_coverage used
during training. In most projects this means min_sample_coverage: 4 when base_config.min_coverage:
4. A higher min_sample_coverage is appropriate only when test samples are known to be
sequenced at substantially higher depth than training centroids and locus-level precision is
paramount.

4.11 Publication Guidance
The most accurate publication description is:
• methyldetector performs nonparametric locus-wise screening,
• applies FDR control through Storey q-values,
• supplements significance with heuristic biological ranking,
• and exports a reduced, weighted empirical-distribution feature set.
When the fixed_dmp_panel path is used, the package should be described as applying a pre-specified
position set rather than performing novel discovery.
The package should not be described as a pure hypothesis-testing engine if the effect-coverage filters
are active, because those filters are explicitly post-test prioritization rules.

5.9 Missing Data Semantics
A practical but important detail is how the classifier handles unavailable loci. The implementation
masks those loci out of the weighted average rather than imputing them with a full modeled
distribution. As a result, the effective evidence for a sample depends on how many DMPs are
observed for that sample.
This is a sensible engineering choice, but it means that the posterior confidence is partly a function
of data availability as well as class separation.

5.10 Publication Guidance
The strongest defensible summary is:
• the binary head is an ECDF-based Naive Bayes style score with optional calibration,
• multi-chromosome fusion is a weighted ensemble,
• multiclass OvR is a reduction from binary heads to a normalized 𝐾-class score,
• pairwise control aggregation is heuristic,
• and fitted chromosome weights are second-stage discriminative models, not part of the original
density model.
That framing is more accurate than calling the entire package a single Bayesian multiclass classifier.

The current implementation does not attempt:

measures empirical variation across repeated pipeline runs; it does not prove generalization bounds.

6.9 Two Workflows Summary
MethylValidation supports two primary operational modes, described in full in Chapter 12. A brief
summary for theory readers:
Workflow 1 — Model Creation. Repeated Monte Carlo runs with --stability estimate DMP
recurrence frequencies from centroid+detector iterations. The --freeze step then builds production
biological outputs on the stable panel (fixed_dmp_panel) and may run progression synthesis.
The --model step then performs final classifier/predictor execution after optional biological gate
checks.
Workflow 2 — Model Use for Prediction. The --predictor-only flag evaluates the frozen
production model on repeated random holdouts without retraining. This workflow answers the
question: what is the empirical distribution of classification performance for the frozen production
classifier under random sampling from the available cohort?
The two workflows share the same split-and-aggregate infrastructure (split.py, project_gen.py,
pipeline_runner.py) but differ in which pipeline steps execute per iteration. Workflow 1 iterations
run centroid+detector; Workflow 2 iterations run predictor only.

7 MethylMapper
7.1 Role
methylmapper converts locus-level detector output into gene- and region-level annotations. It has
two distinct mathematical layers:
1. deterministic genomic mapping through bedtools-style interval logic or an external Azure SQL
stored procedure, and
2. gene-level aggregation and disease-evidence enrichment.
The relevant code lives primarily in:
• packages/methylmapper/methyl_mapper/bedtools_mapper.py
• packages/methylmapper/methyl_mapper/mapper.py
• packages/methylmapper/methyl_mapper/gene_disease_enricher.py

7.2 Interval Mapping
The bedtools path maps DMP coordinates to genomic features such as promoters, exons, introns, and
gene bodies. This part is deterministic interval algebra rather than statistical inference. Feature-level
weights may then be attached, for example promoter weights or exon weights, but those weights are
biological priors chosen by the workflow rather than estimated model parameters.
The Azure SQL path calls a stored procedure (spMapDMP2Genes). Because the stored procedure
logic is external to the repository, its exact mapping semantics should be documented as an external
dependency rather than as a transparent in-repo algorithm.

7.4 Biological Importance Score
calculate_biological_importance() combines detector statistics such as delta_mean, overlap,
and std into a bounded gene- or region-level importance score. This is not a likelihood or hypothesis
test. It is an engineered prioritization score meant to rank biologically interesting genes after
mapping.
Publication text should call this what it is: a heuristic importance score that mixes detector-derived
quantities and feature weights.

7.5 Stable Gene Set Optimization
The package also contains routines that choose the number of top DMPs required to obtain a
stable gene set. These routines are operationally useful, but they are not estimators with standard
sampling distributions. Their parameters, step sizes, and stability thresholds should therefore be
documented as tuning knobs.

7.6 External Evidence Enrichment
GeneDiseaseEnricher queries external services such as DisGeNET (Piñero et al. 2020), Open
Targets (Ochoa et al. 2023), and optional Grok-mediated evidence pipelines. This is a valuable
biological annotation layer, but it is not in-repo statistical inference. The final evidence depends
on:
• service availability,
• service version,
• cached responses,
• threshold profiles such as strict or balanced, and
• optional LLM-assisted synthesis.
For publication, that layer must be framed as external evidence gathering and summarization rather
than as a mathematically identified part of the detector.

8 MethylEnricher
8.1 Role
methylenricher is a downstream interpretation layer. It takes mapped genes or weighted gene lists
and organizes them into pathway-level and module-level summaries. The package mixes three kinds
of methodology:
• external enrichment analysis through Enrichr (Chen et al. 2013),
• graph-based pathway grouping,
• heuristic module ranking and disease-prior labeling.
Because of that mixture, this package should be described as a discovery and prioritization layer,
not as a single statistical model.

8.2 Over-Representation Analysis
The enrichment step is delegated to Enrichr through gseapy.enrichr. In practice this means
the repository submits a gene list to an external enrichment engine and then reads back adjusted
p-values, odds ratios, and gene memberships for the selected libraries.
The statistical test itself therefore lives outside the repository. The in-repo code is responsible for:
• choosing the input genes,
• selecting the enrichment libraries,
• filtering the returned tables, and
• carrying forward the adjusted p-values into later scoring steps.
Publication text should cite Enrichr (Chen et al. 2013) and record the exact library set used in the
analysis.

methylalignmentqc is the least inferential package in the repository. It parses alignment and
duplication metrics produced by external tools such as Picard and Parabricks, then rewrites them
into structured JSON for downstream inspection.
The package therefore belongs in the theory book only so that readers do not over-interpret it. Its
main functions are deterministic parsing, normalization, and reporting.

The parser reads tabular metrics files, histograms, and summary blocks and maps selected fields
into a fixed schema. Typical examples include:
• total reads,
• duplicate counts,
• duplication rate,
• related read-group or library statistics.
There is no new statistical estimator here beyond whatever upstream alignment tool already
computed.

10 Limitations and Open Questions
10.1 Why This Chapter Exists
The repository is scientifically useful, but it is not served well by a perfectly tidy story. The code
mixes exact formulas, approximations, heuristics, and external-service calls. This chapter records
the main caveats that should be understood before publishing claims based on the pipeline.

10.2 The “ECDF-Only Pipeline” Claim Is Too Broad
The centroid-detector-classifier path is indeed ECDF-centered. However:
• methylmapper uses weighted Stouffer aggregation and heuristic importance scores,
• methylenricher uses external enrichment plus heuristic module scoring,
• methylalignmentqc is deterministic QC parsing, not ECDF inference.
Therefore the monorepo as a whole should not be marketed as purely ECDF-only. The safer
statement is that the core supervised detection and classification path is ECDF-centered.

10.3 Dependence Is Real
Several methods rely on assumptions that are standard but imperfect for methylation data:
• loci within one chromosome are correlated,
• mapped DMPs within one gene are correlated,
• binary OvR heads are not guaranteed to be jointly compatible,
• repeated validation splits are not independent external studies.
This does not invalidate the workflow, but it does change how literally one should interpret p-values,
q-values, and meta-analytic combinations.

10.4 Approximation Layers
The code intentionally trades exact raw-data procedures for scalable summaries:
• KS statistics are evaluated on a grid and calibrated asymptotically,
• Mann-Whitney is reconstructed from histograms rather than raw ranks,
• ECDF overlap is integrated numerically after spline reconstruction,
• some distance calculations average only over pairwise-overlapping loci.

45

These approximations should be reported as approximations, not hidden behind textbook method
names alone.

10.5 Heuristic Layers
The following components are best described as engineering decisions:
• the canonical effect-size ranking,
• cumulative effect-mass selection,
• geometric-mean control aggregation for pairwise OvR bundles,
• module scoring constants in methylenricher,
• stability thresholds for choosing top DMP counts in methylmapper,
• auto-cap rules for coverage trimming.
These are often useful, but their outputs are not calibrated probabilities or test statistics.

10.6 External Dependencies
Some results depend on systems whose internal logic is not fully versioned inside this repository:
• Enrichr,
• DisGeNET,
• Open Targets,
• Azure SQL stored procedures,
• optional Grok/xAI-assisted evidence synthesis.
Any publication using those layers should record service versions, access dates, and cache policies.
Otherwise the results are reproducible only in a weak operational sense.

10.7 Legacy Or Experimental Remnants
Several code paths look incomplete or partially superseded:
• packages/methylutils/comparison.py still advertises beta-based comparison logic that
does not match the active ECDF-first production path.
• Some older package docs still describe a stricter or cleaner theory story than the code currently
supports.
These remnants do not have to be deleted immediately, but they should not be cited as active
method descriptions.

46

10.8 Publication-Ready Positioning
The strongest defensible manuscript framing is:
1. the core pipeline summarizes methylation into centroids with empirical distributions,
2. it detects DMPs with nonparametric, ECDF-based screening and FDR adjustment,
3. it classifies samples with weighted empirical-distribution likelihoods,
4. and it layers biological annotation and pathway-level interpretation on top.
Anything stronger than that risks overstating what the code actually does.

10.9 What Would Strengthen The Theory Further
The current implementation could support stronger future papers if the repository adds:
• finite-sample benchmarking of histogram-based Mann-Whitney against raw-rank MannWhitney,
• calibration studies for the effective-temperature ECDF classifier,
• dependence-aware gene aggregation,
• more explicit modeling of multiclass consistency,
• and clearer retirement or isolation of legacy experimental branches.
Those are natural next steps, but they are not yet the state of the codebase.

12.2 Workflow 1: Model Creation
12.2.1 Theoretical Motivation
A naive approach to building a classifier would be to detect DMPs on all available samples, then
evaluate the same classifier on held-out subsets. This conflates feature selection with performance
estimation: the DMP panel was implicitly chosen to fit all samples, making any leave-out evaluation
optimistic.

56

MethylValidation addresses this by repeating only the discovery portion of the pipeline on random
train/validation splits. Each iteration rebuilds centroids and re-runs detection on the training cohort
only. The resulting detector-side balanced accuracy summaries are used as internal estimates of
discovery robustness and to filter stability runs when requested.
After many such iterations, a DMP that appears consistently in the discovery sets of most runs is
more likely to reflect a true biological signal than one that appears in only a few. This motivates
the stability analysis: the stable panel is a consensus over repeated random partitions of the data.
The production freeze then trains a final classifier on all available data restricted to the stable
panel. Because the panel itself was selected using the full sample set (via the MC iterations), this is
still an internal analysis; it is not a substitute for external validation on an independent cohort.

2. rebuilds centroids on all data,
3. runs detector in fixed-panel mode,
4. runs mapper and enricher to produce gene/pathway outputs,
5. optionally runs progression synthesis for ordered disease-stage summaries.
The freeze artifacts (production/project.json, fixed-panel detection outputs, mapper/enricher
summaries) become the canonical handoff package for model release and review.

Theoretical role. This stage fits the final prediction function conditioned on the frozen panel
and frozen production project. It separates feature agreement (handled in Stage A/B) from final
classifier parameter estimation (handled here).
Practical role. This stage answers: “What trained classifier and predictor artifacts should be
deployed?” In practice it:
• runs methyl-classifier on production/project.json,
• runs methyl-predictor to generate production-side metrics/artifacts,
• enforces the optional biological gate (require_biological_review_for_model) before model
creation.
The resulting files under production/classifiers/ and production/predictors/ are the deployable model artifacts. Any rerun with changed panel or freeze inputs should be treated as a new
model version.

12.3 Workflow 2: Model Use for Prediction
12.3.1 Theoretical Motivation
Once a production model exists, a natural question is: what balanced accuracy does it achieve on
random holdouts drawn from the available cohort? This is not the same as the BA measured in
Workflow 1, because Workflow 1 re-trained the model on each split while Workflow 2 applies the
frozen model.
Workflow 2 provides the empirical distribution of the frozen model’s performance under random
sampling. It is faster than Workflow 1 (only the predictor runs per iteration), and it answers the
question: is the production model’s accuracy stable across different random splits, or does it depend
heavily on which specific samples are held out?
Important caveat. The available cohort used in Workflow 2 overlaps with the training data for
the production model (the production model was trained on all samples). This means Workflow 2 is
not a hold-out evaluation in the classical sense; the test samples may also be in the training centroid.
A truly external validation cohort would be needed to measure generalization to unseen data.

1. Creates a new split-specific project.json with train/validation CSVs.

12.4 Diagnostic: DMP Coverage
Symptom. sample_dmp_coverage.dmps_used_fraction_median < 0.5 in validation_metrics.json.
Values below 0.3 indicate severe degradation.
Cause. The centroid min_coverage (e.g. 4) and the detector min_sample_coverage (default 10)
are mismatched. DMP positions that were detectable in training centroids at 4× coverage become
invisible in test samples when the classifier requires 10× coverage.
Fix. In step_config.detection, add:
"min_sample_coverage": 4

62

This aligns the coverage requirement for classification with the centroid build threshold.
Verification. Re-run Workflow 2. dmps_used_fraction_median should rise to 0.6–0.9 for typical
WGBS data.

12.5 Diagnostic: Class Imbalance
Symptom. The confusion matrix shows near-perfect recall for the majority class (e.g. healthy/control) and near-zero recall for minority classes (disease stages). Balanced accuracy is close to 1/K
(random chance).
Cause. The training cohort has substantially more samples in one class. For example, 86 healthy
vs 25–36 disease samples per stage (41% healthy in the example project). The multinomial logistic
regression learned head defaults to the majority class when the histogram scores are ambiguous
(which is common when DMP coverage is low).
Fix. In step_config.detection, add:
"multiclass_train_learned_head": true,
"multiclass_learned_class_weight": "balanced"
The balanced setting computes 𝑤𝑘 = 𝑛total /(𝐾 ⋅ 𝑛𝑘 ), penalizing majority-class errors proportionally
less than minority-class errors. See § 5.8 for the full derivation.

12.6 Diagnostic: Sklearn Version Mismatch
Symptom. Warning messages during prediction: InconsistentVersionWarning: Trying
to unpickle estimator LogisticRegression from version X.Y.Z when using version
A.B.C.
Cause. The multiclass-classifier.pkl was serialized with a different version of scikit-learn
than the one currently installed.
Diagnosis. Check the sklearn_version field in the model PKL metadata:
import pickle
with open("monte_carlo_runs/production/classifiers/multiclass-classifier.pkl", "rb") as f:
model = pickle.load(f)
print(model["metadata"].get("sklearn_version")) # version used at training time
Compare to the current installed version:

import sklearn; print(sklearn.__version__)
Fix. Re-run the --freeze step with the current sklearn version. The logistic regression head will
be retrained and the new PKL will record the correct version. New model PKLs produced after the
fix always record sklearn_version in their metadata.

12.7 Choosing Workflow Parameters
12.7.1 train_fraction
Higher values (0.8–0.9) leave less data for validation but produce more powerful centroids in training.
For small cohorts (total 𝑛 < 50 per class), prefer 0.8. For large cohorts, 0.9 is reasonable.

12.7.2 n_iterations
More iterations reduce the variance of the empirical performance summaries. 20–50 iterations is
typically sufficient to characterize the mean and standard deviation of balanced accuracy. 100+
iterations are useful for stable percentile estimates (e.g. p5, p95).

12.7.3 stability_dmp_freq
Higher values (0.8–1.0) produce smaller, more reproducible panels but may miss positions that are
biologically informative but variable across splits. Lower values (0.5–0.7) retain more positions at
the cost of including split-sensitive noise. A good starting point is 0.7.

12.7.4 stability_min_balanced_accuracy
Setting this parameter (e.g. to 0.6) excludes iterations with poor validation performance from the
DMP frequency count. This can improve panel quality by excluding outlier runs where the centroid
construction or detection failed to find informative DMPs. It also reduces the effective R* and thus
̂
increases the variance of 𝑓(𝑑).
Use with caution for small n_iterations.

14.3 Workflow 1: Model Creation
Full theoretical background: § 12.2.

14.3.1 Stage-oriented execution checklist
Workflow 1 should be run and reviewed in three explicit stages:
1. Stability (--stability): optimize panel robustness (n_iterations, train_fraction,
stability_dmp_freq) and verify stable_dmps_production.csv is non-empty and
biologically plausible.
2. Freeze/analysis (--freeze): lock the panel into production/project.json, then review
production detector outputs together with mapper/enricher summaries.
3. Modeling (--model): train final classifier and predictor artifacts only after stability and
biological review are complete.
Treat changes in any of these stage inputs as a model version change, not as a minor rerun.

14.3.2 Step 1: Run Monte Carlo with stability
source .venv/bin/activate
methyl-validation --project configs/my_project.json --stability
This runs n_iterations Monte Carlo discovery cycles (centroid → detector), then aggregates DMP
recurrence frequencies.
Monitoring progress. Progress is shown via a Rich progress bar in interactive terminals. Iteration
logs are written to monte_carlo_runs/run_000N/logs/.
Useful flags: - --iterations N — override n_iterations from config for a quick test run - --seed
S — override the seed - --skip-enricher — skip enricher during --freeze (and progression, if
enabled)

14.3.3 Step 2: Check stability results
After the loop completes, review the stability output:
cat monte_carlo_runs/stability/stability_summary.json
head monte_carlo_runs/stability/stable_dmps_production.csv
The summary reports: - n_runs_analyzed — number of qualifying runs - total_unique_dmps —
total unique positions across all runs - stable_dmps_at_threshold — positions with frequency �
stability_dmp_freq
If stable_dmps_at_threshold is very low (< 1000), consider reducing stability_dmp_freq or
increasing n_iterations.

14.3.4 Step 3: Run the production freeze
methyl-validation --project configs/my_project.json --freeze
This runs the production freeze pipeline on all samples using the stable DMP panel (centroid →

14.7.4 Confusion matrix interpretation
The confusion matrix is indexed [true_class][predicted_class]. A model biased toward the
majority class (e.g. healthy) shows high recall for class 0 (all) and near-zero recall for all other
classes. This is the primary symptom of class imbalance (§ 12.5).

14.8 Three Key Diagnostics
14.8.1 Diagnostic 1: Low DMP Coverage
Symptom: sample_dmp_coverage.dmps_used_fraction_median < 0.5 in validation_metrics.json.
All cancer classes predicted as healthy.
Root cause: min_sample_coverage in step_config.detection is higher than the centroid
min_coverage in step_config.centroid.base_config.
Fix: Align both thresholds:
"centroid": { "base_config": { "min_coverage": 4 } },
"detection": { "min_coverage": 4, "min_sample_coverage": 4 }
Verification: After re-running, check dmps_used_fraction_median in the new run’s
validation_metrics.json. Expected range: 0.6–0.95.
See § 4.10 for theoretical background.

98

14.8.2 Diagnostic 2: Class Imbalance
Symptom: Confusion matrix shows recall � 1.0 for the majority class (e.g. healthy/control) and
recall � 0 for all disease classes. Balanced accuracy close to 1/K.
Root cause: The training cohort has substantially more samples in one class. The multinomial
logistic head defaults to the majority class when histogram scores are ambiguous.
Fix:
"detection": {
"multiclass_train_learned_head": true,
"multiclass_learned_class_weight": "balanced"
}
This sets 𝑤𝑘 = 𝑛total /(𝐾𝑛𝑘 ) in the logistic regression. Note that multiclass_train_learned_head:
true is required for multiclass_learned_class_weight to take effect.
Verification: Re-run. The confusion matrix diagonal should become more balanced. Per-class
recall should be non-zero for all classes.
See § 5.8 for theoretical background.

14.8.3 Diagnostic 3: Sklearn Version Mismatch
Symptom: InconsistentVersionWarning during prediction. The model was trained with sklearn
X.Y.Z but is being run with A.B.C.
Check:
import pickle, sklearn
with open("monte_carlo_runs/production/classifiers/multiclass-classifier.pkl", "rb") as f:
model = pickle.load(f)
print("Trained with sklearn:", model["metadata"].get("sklearn_version"))
print("Current sklearn:
", sklearn.__version__)
Fix: Re-run --freeze with the current sklearn version. The new PKL will be trained with the
current version and record it in metadata.
Long-term: Pin scikit-learn to a specific version in your environment to avoid future mismatches.
